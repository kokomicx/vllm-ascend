## 三、优化建议

### 建议 1：Slide 22 根因分析——建议加入"Spec 设计"作为第三个源头

当前 Slide 22 的描述：
- 硬件约束: NPU算子不支持stride访问 → 根因1~5
- 接口缺陷: get_kv_cache_shape() 单返回值 → 根因6

**缺失**：我们在文档 §7.8 中详细论证了 "Spec 万能类: 类型擦除" 是与硬件、接口并列的独立根因。它不是硬件问题的派生——即使 NPU 支持 stride，如果 Spec 仍然是万能类，model_runner 仍然要靠 if-else 区分 5 种 MLA 变体。

建议将 Slide 22 的根因 3 从 "Sparse 多 Tensor" 改为 **"Spec 万能类: 类型擦除"**（MAGENTA 色），callout 从"两个源头"改为"三个源头"：

```
三个根本源头:
  硬件约束: NPU算子不支持stride访问 → host侧必须预拆分 → 根因1,2,4,5
  Spec 设计: 类型不编码语义 → isinstance()无区分力 → 下游if-else恢复丢失的类型信息 → 根因3
  接口缺陷: get_kv_cache_shape() 单返回值无法表达多tensor布局 → 根因6
```

**理由**：Spec 子类拆分是 Ascend 完全可控的（不需要等算子侧），而且 `AscendSlidingWindowMLASpec` 已经证明正确的拆分是可行的。把它从硬件根因中独立出来，Phase 1 的 Spec 拆分任务就更有说服力。

### 建议 2：Slide 14 对比表——加入上游参照列

当前 Slide 14 的表格只展示了 Ascend 侧的信息（Spec 类 / Backend / Allocate tensors / Reshape 方式 / 核心复杂度）。建议参考我们重构后的版本，每列同时显示"上游 → Ascend"的对照，让观众一眼看到差距。

### 建议 3：社区速览部分的节奏

Slide 4-8（5 页社区知识速览）信息密度很高。建议在 Slide 4 之后加一页过渡——"社区方案的三个核心设计原则"——用 3 句话总结：
1. **Backend 说了算**：KV Cache shape 的唯一决定者
2. **单 tensor 原则**：所有模型类型都产生 1 个 tensor/层
3. **model_runner 零感知**：不检查 layer_type，不判断模型差异

这样观众在进入 Ascend 对比之前，脑子里有清晰的"社区三原则"，对比效果更强。
