KV Cache 存储什么？

核心概念

Transformer 推理时，每个 token 的 attention 需要访问所有之前 token 的 Key 和 Value。 如果每步重新计算，复杂度是 O(n²)。KV Cache 把已计算的 K、V 缓存起来， 新 token 只需算自己的 Q、K、V，然后从缓存读历史的 K、V。

存储的量

量Shape说明
key_cache[num_blocks, block_size, H_kv, D]所有历史的 Key
value_cache[num_blocks, block_size, H_kv, D]所有历史的 Value
block_table[num_requests, max_blocks]请求 → 物理 block 映射
slot_mapping[num_tokens]每个 token → 物理地址

Qwen2.5-7B 举例

# 每层 KV Cache 形状
key_cache:   [32 blocks, 128 tokens, 4 KV heads, 128 dims]
value_cache: [32 blocks, 128 tokens, 4 KV heads, 128 dims]

# 每个物理 block 大小
block_size  = 128  tokens
page_size   = 128 × 4 × (128+128) × 2 bytes
            = 256 KB

# 28 层, 32 blocks: 总 ≈ 224 MB

设计思想：PagedAttention 核心模式

类比 OS 虚拟内存分页

OS 概念PagedAttention 对应
物理页框Physical Block (固定大小的 KV 存储单元)
页表Block Table (请求 → block_id 序列)
虚拟地址Slot Index (token 在序列中的位置)
物理地址Slot Mapping (block_id × block_size + offset)
空闲页框链表FreeQueue (可分配的 block 队列)
共享内存Prefix Cache (多个请求共享相同前缀的 block)

为什么用分页？

传统方式为每个请求预分配 max_seq_len 的连续内存 → 严重内存碎片 + 浪费

PagedAttention 按需分配 block，请求用多少给多少 → 零碎片 + 按需增长

Free Queue
block_3, block_7, ...
→
Req A
[block_0, block_1]
Req B
[block_2]

两个请求的 KV cache 分散在不同的物理 block 中，Block Table 记录映射关系

KVCacheSpec 体系 驱动者

继承链 — 纯数据，零行为

KVCacheSpec                         # block_size, page_size_bytes
  └─ AttentionSpec                     # +num_kv_heads, head_size, dtype
       ├─ FullAttentionSpec              # +head_size_v, sliding_window

       └─ Enc​oderOnlyAttentionSpec

↑ 都是 @dataclass(frozen=True) — 不可变，声明式。"是什么"，不定义"怎么做"

关键属性：page_size_bytes

class FullAttentionSpec:
    def real_page_size_bytes(self):
        return (
            2                      # K + V
            × self.block_size      # 128 tokens
            × self.num_kv_heads   # 4 heads
            × self.head_size      # 128 dims
            × get_dtype_size(self.dtype) # 2 bytes
        )
        # = 2 × 128 × 4 × 128 × 2 = 262,144 bytes = 256KB

allocate 函数只需要这一个数就能算出 num_blocks。不知道 K、V 各自的 dim，不需要知道。

上游 vLLM allocate ~15 行 · 0 分支

完整代码

def _allocate_kv_cache_tensors(self, kv_cache_config):
    kv_cache_raw_tensors = {}
    for kv_cache_tensor in kv_cache_config.kv_cache_tensors:
        tensor = torch.zeros(
            kv_cache_tensor.size,      # ← KVCacheTensor 已算好的字节数
            dtype=torch.int8,          # ← 统一 int8，延迟类型绑定
            device=self.device
        )
        for layer_name in kv_cache_tensor.shared_by:
            kv_cache_raw_tensors[layer_name] = tensor  # 共享同一块内存

    return kv_cache_raw_tensors

为什么如此简洁？

  • KVCacheTensor.size 在上游 get_kv_cache_config 已经算好
  • dtype=torch.int8 是按字节分配，reshape 时再 .view(bf16)
  • shared_by 让多层共享同一块物理内存（同一个 tensor 对象）
  • 不需要知道是 GQA 还是 MLA — 那是 reshape 的事

上游 vLLM reshape Spec + Backend 多态

def _reshape_kv_cache_tensors(self, raw_tensors, kernel_block_sizes):
    for group in self._attn_group_iterator():
        spec   = group.kv_cache_spec     # ← "是什么" (数据)
        backend = group.backend           # ← "怎么做" (多态)
        for layer_name in group.layer_names:
            raw = raw_tensors[layer_name]
            num_blocks = raw.numel() // spec.page_size_bytes  # Spec 提供
            kernel_N   = num_blocks × (spec.block_size // kernel_B)

            shape = backend.get_kv_cache_shape(           # Backend 提供
                kernel_N, kernel_B,
                spec.num_kv_heads, spec.head_size,     # Spec 提供参数
            )
            stride_order = backend.get_kv_cache_stride_order() # Backend 提供

            kv_cache = raw.view(spec.dtype).view(shape).permute(*inv_order)
            kv_caches[layer_name] = kv_cache

为什么 Ascend 做不到和上游一样简洁？

Ascend 硬件特有的三个需求

① K/V 物理分离

Prefill Disaggregation (PD) 需要 K 和 V 的地址独立 2MB 对齐， 以支持 RDMA 传输。上游把它们叠在一个 tensor 的 dim0=2 上，Ascend 必须分开分配。

② Sparse MLA 多 tensor

DeepSeek V3.2 的 indexer 模块产生独立于主 KV 的 key tensor。 需要 3-tuple (无 C8) 或 4-tuple (有 C8: int8 key + fp16 scale)。

③ Compressed MLA as_strided

DeepSeek V4 的压缩存储 (compress_ratio=4/128) + fp8 + per-token scale。 需要在一个 buffer 上覆盖多个 as_strided view。

结论

上游只需要 2 层多态：Spec + Backend。
Ascend 需要 3 层多态：Spec + Layout + Backend。

问题不在于"需要更多层"——而在于当前的实现方式是把 Layout 的决策硬编码在 allocate/reshape 的 if-else 里，而不是封装成一个可多态的接口。

重构方案：引入 KVCacheLayout 第三层多态

新接口

class KVCacheLayout(ABC):
    """物理内存布局策略 — 第三层多态"""

    def num_tensors(self) → int: ...
    # 几种 tensor? 1 / 2 / 3 / 4

    def split_sizes(self, total: int, spec) → list[int]: ...
    # 总字节数如何分给各个 tensor?

    def reshape(self, raw, spec, N, kN, kB, backend):
    # raw int8 → 多维 tensor(s)

    def needs_alignment(self) → bool: ...
    # 是否需要 2MB 对齐?

Spec 上的挂载点

class AscendMLAAttentionSpec:
    def get_kv_cache_layout(self):
        if self.compress_ratio > 1:
            return CompressedMLALayout()
        if self.cache_sparse_c8:
            return SparseMLAC8Layout()
        if self.sparse_head_dim is not None:
            return SparseMLALayout()
        return SplitMLALayout()
# ↑ 这些 if-else 在 Spec 内部，不在 allocate/reshape

def _reshape_kv_cache_tensors(self, raw, kernel_block_sizes):
    for group in self._attn_group_iterator():
        spec, backend = group.kv_cache_spec, group.backend
        for layer_name in group.layer_names:
            layout = spec.get_kv_cache_layout()   # ← 唯一分发点

            raw_list = raw[layer_name]
            if not isinstance(raw_list, (list, tuple)):
                raw_list = [raw_list]

            N  = sum(t.numel() for t in raw_list) // spec.page_size_bytes
            kN = N × (spec.block_size // kernel_block_size)

            kv_caches[layer_name] = layout.reshape(
                raw_list, spec, N, kN, kernel_block_size, backend
            )
